# 研究就緒資料快取實作任務

對應設計：[research-data-cache-design.md](research-data-cache-design.md)；需求：[research-data-cache-requirements.md](research-data-cache-requirements.md)。

**狀態：T1～T4 已完成並驗收（T3 實作時拆為 T3a 算術接續、T3b `update_cache`、T3c `rebuild_cache`）。**

## 執行規則

- 依序執行；前一任務未通過 main agent 驗收，不開始下一任務。任務會改同一批檔案，不並行。
- 每項任務委派給 `system-execution-agent`（`agentScope: "user"`，`cwd` 為專案根目錄絕對路徑），單一模式；task 以英文撰寫，含目標、限制、輸入、輸出、驗收條件與必要證據。
- 真實資料操作一律唯讀，受記憶體上限與逾時限制；不 commit、不 push。
- 不符合驗收：指出失敗的需求與修正指示，只做必要修改，修正後 main agent 重新驗收。
- 文件（使用說明、狀態更新）由 main agent 在 T4 後撰寫，不委派。
- 每項任務的證據須列出對應 V 項目的測試名稱與案例，並附 `git status --short` 與新增測試檔路徑（新增檔案不會出現在 `git diff --stat`）。
- 任何階段若發現來源被修改、涵蓋期間被錯誤改變或回復（rollback）失效，立即停止並回報。

## T1：行為保持不變的拆分（設計 §9）

**目標：** 為快取重用拆分既有程式；既有行為不變。

**範圍：**
1. 先對既有 `load_taiwan` 測試資料記錄基準（各情境 `input_digest`），存於 `/tmp`。
2. `build.py`：拆出「讀原價報價＋分類＋品質旗標」函式，`_iter_series_from_reader` 改為組合它與既有的事件＋調價。拆出的函式須：(a) 能在正規化前依代碼略過報價（供非 4 位數捷徑，使用與 Dataset 相同的 ASCII 形狀判斷）；(b) 以選用的錯誤回呼支援「單一標的正規化失敗不中止其餘標的」，預設維持現行 fail-fast。
3. `research/taiwan.py`：抽出「由每檔序列產生 `Bar`／`CorporateAction`」的共用函式（明確接收被固定的 reader 及其事件摘要／明細所需資料），`load_taiwan` 改為呼叫它們。

**驗收：** V0；`git diff --stat tests/` 與 `git status` 顯示既有測試檔未被修改（可新增測試）；預設錯誤行為與暫存作業區清理有測試。
**證據：** 測試與 lint 輸出、digest 對照表、`git status --short`。

## T2：快取核心——儲存、首次建立、不可用標的、讀取

**目標：** 設計 §3、§4、§5 共通規則、§6：`build_cache`、`load_cached`、`cache_status`、`list_symbols`。

**範圍：** `research/cache.py`（新增）、`research/__init__.py` 匯出、測試（合成資料，沿用 `tests/test_research_taiwan.py` 的來源資料建置輔助函式）。含 schema 與版本檢查、WAL 與單一寫入交易、路徑保護、證據雜湊記錄、非 4 位數捷徑、分類範圍、單檔失敗隔離與驗證、不可用紀錄、`sessions`／`scopes`、`calendar_basis`、`protected_input_dirs`、讀取端錯誤與涵蓋範圍檢查。

**驗收：** V1、V4（建立與讀取部分）、V5（首次建立）、V6；既有測試、ruff、mypy 通過。
**證據：** 測試輸出、V1 比對測試位置、V4 各錯誤案例清單。

## T3：連乘接續、增量補建與起始日重建

**目標：** 設計 §5、§5.1：`process_quotes` 的接續參數、`update_cache`、`rebuild_cache`、證據雜湊檢查、更新時已存標的失敗轉為不可用、不可用標的的恢復規則。

**範圍：** `arithmetic.py`（兩個選用關鍵字參數，預設行為不變，含單元測試：接續結果等於不中斷計算，含循環小數倍率、空窗期事件、首筆新增報價當日事件）、`cache.py`、測試。

**驗收：** V2、V3、V7、V4 的更新時失敗案例、V5（update／rebuild）；V0 重跑（算術被修改）；以正規內容逐字比較，不用容差；既有算術測試未修改且通過。
**證據：** 測試輸出、V2／V3 案例清單。

## T4：本機真實資料唯讀驗證與冒煙量測（V8）

**範圍：** 在 `/tmp` 建立快取（不在 repo、不在資料根目錄內）：
1. 少量標的核對快取與 `load_taiwan` 逐欄一致。
2. 保留尾段的更新實測：以較早的結束日建立，再更新到最新，與一次完整建立到最新的正規內容比對（少量標的）。
3. 冒煙量測：選至少三個不同資料量 N（以報價筆數計，例如約 1 萬、10 萬、50 萬筆，標的取自同一市場且彼此為包含關係），各自量測 `build_cache` 與 `load_cached` 的耗時、峰值記憶體、暫存空間、WAL 峰值、快取檔大小。每個 N 在獨立子程序執行。
4. 依各 N 的量測值檢查近似線性（報告每步的比例），再比例推估全部範圍內標的（約 380 萬筆報價）的各項數值；報告須標明「推估」、推估所用的點與公式。
5. 複製使用中的快取時使用 SQLite backup，或在關閉並檢查點後複製。

**限制：** 唯讀資料根目錄；以 `systemd-run` 記憶體上限（建議 20 GiB）與逾時保護機器；失敗是有效結果，如實記錄，不為通過而改程式；前後記錄 `state.sqlite3`／`-wal` 的 size 與 mtime，並在使用證據檔案時一併記錄。不要求、也不執行全量建立。
**驗收：** 小範圍逐欄一致；更新實測與完整建立相同；至少三個 N 的量測值與原始日誌齊全，並有標示為推估的全量數字與其公式。若量測點不近似線性，如實報告並說明推估的不確定性，不調整數字。
**證據：** 日誌路徑、數據表、資料根目錄前後 stat。

## 最終驗收（main agent）

重跑全部測試、ruff、mypy；抽核 T4 日誌；對照 RDC-01～13 逐項勾稽；撰寫使用說明（含已知限制與價格使用說明，RDC-08、09、12），更新 README 與各文件的狀態欄；以 `rg` 檢查文件無本機絕對路徑；提交前依 AGENTS.md 完成公開 repo 檢查（僅在使用者要求 commit 時）。

## 風險與停止條件

- T1 digest 與基準不同：停止，找出原因後才繼續。
- T3 增量與完整重建無法逐字相同：停止，回到設計 §5.1 討論，不以容差掩蓋。
- T4 冒煙量測中任一 N 失敗或明顯非線性：如實回報，與使用者討論，不自行改範圍、不改成分批提交。
- 磁碟空間不足（暫存區、快取、WAL）前停止，而不是用盡後失敗。
- 無效能通過門檻；使用者決定只以冒煙加推估取得規模數字。
